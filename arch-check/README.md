# @v1d/arch-check

Rules as data in `arch.config.json`; old debt as counts in `arch.baseline.json` that may only shrink.

    node arch-check.mjs [repo]            check (exit 1 on any hit or stale baseline entry)
    node arch-check.mjs [repo] --init     write the baseline from today's counts (first time only; refused once it has entries)
    node arch-check.mjs [repo] --lower    lower the baseline to today's counts; never raises
    --today YYYY-MM-DD                    read each rule's failsFrom against this day (0.18.0), to see a told rule as it will fail
    --amux-root DIR                       where AMUX is, for a `contract` rule (else $AMUX_ROOT, else the amux on PATH)

A hit reads `rule N name: file:line message. Fix: ...`.

`KEY_NAMES` (`providers`, `modal`) exports the two key-name matchers alone, for a check of live secrets by name.

Kinds (each rule has `id`, `name`, `kind`, `fix`; `files` and `exclude` are globs with `*` and `**`):

- `max-lines` `{max, count?, split?}`: a file over max; the excess counts toward the baseline. With `count: "code"` (0.19.0, Cut push-protocol-14) a blank line and a line that is only a comment are not counted, and the hit says both numbers (`612 lines of code (803 lines), max 600`); in the guard `count` changes only by a decision (`ceilings <id>:count: 1`). `split: {from, lands}` holds a push, see `touched`.
- `providers` `{}`: a line that names an AI provider's host, imports its SDK (JS or Python) or names its key is red: only ai-gateway calls a provider, and a provider key lives only as an ai-gateway secret. The list is `PROVIDERS` in arch-check.mjs, the same for every repo; `files` defaults to code and config, and the places a repo still has sit in its baseline, which may only shrink. ai-gateway does not turn it on.
- `modal` `{}`: the same for Modal (`MODAL` in arch-check.mjs): its SDK, a `*.modal.run` address, its token and an app's own address of a Modal app (`STATELESS_URL`, `EXECUTOR_URL` and the like) are red; only ai-gateway starts Modal work.
- `max-line-length` `{max}`: a code line over max characters (counted as characters, not UTF-16 units), so no file keeps under its `max-lines` by packing its lines. Comment lines (`//`, `/*`, `*`, and `#` in a language that writes its comments so) and generated files (`generated` in the path, or `GENERATED by`, `@generated` or `Do not edit` in a comment of the first five lines) are left out. The excess characters count toward the baseline, so a long line of the baseline cannot grow either; in the guard its `max`, `exclude` and kind change only by a decision, as for `max-lines`.
- `max-module-lines` `{in, max, caps?}`: a module is each folder directly under one of `in`; the lines of its covered files are summed (the lines an editor numbers), so a module can be read at one go. A file directly in an `in` folder belongs to no module. The limit is `caps[folder]` where the rule names one, otherwise `max`: a module that is already over `max` keeps its own cap, and in the guard a cap only drops (a raise, or a new cap above `max`, needs a decision `<id>:cap:<folder>`; a folder that leaves `in` needs `<id>:in:<folder>`).
- `max-files` `{max}`: a folder with more files than max.
- `pattern` `{pattern, flags?, message?}`: a regex per line (comment lines skipped).
  A line opens a comment with `//`, `/*` or `*` in every file, and with `#` only in a file whose language writes its comments so (`HASH_COMMENTS` in rules.mjs:
  Python, shell, YAML, TOML, Ruby, a Makefile, a Dockerfile and the like). Elsewhere a line that starts with `#` is code: a CSS id selector, a JS private
  name, a Markdown heading (0.17.2; up to 0.17.1 it was skipped in every file, so a CSS rule written after an id selector was never counted). A shebang is skipped.
- `absent` `{paths}`: a path that must not exist.
- `folders` `{allow, in?}`: a folder directly under the repo's root (or under `in`) that is not in `allow` is red; node_modules, dist, build, .git and dot folders are left alone.
- `names` `{files, pattern, flags?}`: the name of each covered file, without its folders, must match the regex.
- `modules` `{modules: [{dir, imports}]}`: a module is reached only through its `index`, and only along the listed edges.
- `duplicates` `{lines?, minChars?}`: the same run of lines in two files.
- `contract` `{}`: the first comment of each file has exactly one `WHAT:` and one `WHY:`, and the words pass AMUX's `core/contract-lint.mjs` (`evaluateContract`: a WHAT that opens with one of its verbs, at most 16 words in the WHAT and 18 in the WHY, no filler, a boundary in the WHY); its errors and its warnings are both red, as in Product Studio. AMUX is found by `--amux-root`, `$AMUX_ROOT` or the `amux` on PATH, never by the config. Without it the run stops with exit 2, also with `--init` and `--lower`, and never reads as a pass.
- `css-imports` `{files, scripts, prefix, exclude?}`: a stylesheet (`files`) names a class that starts with `prefix` and that another folder's script (`scripts`) draws, while its own folder's script does not import that folder; a class no script names is nobody's, and `exclude` leaves out the scripts that draw nothing (examples). One hit per class in a stylesheet.
- `one-owner` `{files, of | in, exclude?}` (0.18.0, Huset's rule 31): a class name the covered stylesheets style has one owner. A sheet's owner is the
  innermost folder of the `modules` rule `of` names (its `modules[].dir`), else the folder directly under one of `in`, else the sheet itself. A class styled
  by two or more owners is one hit, keyed by the class (`N:.name`) at its first sheet and line in path order, weighing the owners past the first. A selector
  is the text before a `{` after the last `;`, so a value such as `url(a.svg)` names no class; at-rules and comments name none.
- `count` `{module, export, path | paths, min}`: every item `path` reaches (`*` visits each key; with `paths` the entries of all of them are summed) holds at least `min` entries; a value that is there counts, a list counts its entries; the module is imported, so a `.ts` module needs `node --import tsx`.

## In a browser (`web.mjs`, since 0.16.0)

    import {lint} from "@v1d/arch-check/web";
    const {hits, counts, red} = await lint({files: {"src/a.ts": text}, rules, ts, eslint: {Linter, parser, plugins}, decisions, baseline});

Files given as text, judged by a rule set with the node run's own kinds: those that read text (`rules.mjs`: `max-lines`, `max-line-length`,
`max-module-lines`, `one-owner`, `pattern`, `providers`, `modal`, `duplicates`; `story.mjs`: `eslint`, `first-line`, `story-order`, `stepdown`,
`stepdown-order`, `exceptions`). The gate holds its hits equal to the node run's. A kind that reads a repository's layout or runs its code
(`max-files`, `names`, `folders`, `absent`, `modules`, `css-imports`, `contract`, `count`) is refused by name, and so is a Python file for a story
kind (python3 reads it).
`web.mjs`, `rules.mjs` and `story.mjs` use no node API. The caller brings TypeScript 5 (`ts`) for the story kinds and, for eslint rules, ESLint's
`Linter` (`eslint/universal`), `@typescript-eslint/parser` and the plugins by prefix (`{sonarjs}`). Bundled for a browser, the parser needs `path`
(path-browserify) and no other node module while it runs. A hit is `{rule, file, line, message, weight}`; `check()` returns the hits too.

## Code health report (`--report`, since 0.17.0)

    arch-check <repo> --report [--rev origin/master] [--since <commit>] [--repo cut] > latest.json

One JSON line about a commit, read from git (never the disk), for dash.v1d.io's Code tab: `{repo, sha, at, since, rules: [{id, name, what, why,
fix, total, top: [{key, n}]}], near: [{file, lines, limit}], grew: [{key, from, to, decision}], decisions: [{key, until}]}`. `total` is the rule's
sum in the baseline (null for a report rule) and `top` its ten biggest entries. `near` lists files 0 to 2 lines under a `max-lines` limit as an
editor numbers them; the kind also counts the empty piece after the last newline, so a file at the limit can be one over it and in the baseline.
`grew` compares with `since`, by default the last first-parent commit from a day before: an entry higher than there, or new, in a rule that commit
had (a new rule's entries are its first baseline), with `{who, when, until}` of the decision whose ceiling allows it, or null. A commit without
`arch.config.json` stops the run by name.

## The guard (`guard/`, since 0.9.0)

For a repository that wants its architecture held, not only reported. A repository keeps one small pinned wrapper (it checks the sha256 of this package's `.mjs` files before it imports anything) and runs `runGuard({root, args})` from `@v1d/arch-check/guard/run.mjs`:

- **Doors, dependencies and cycles.** A `modules` rule with `exactEdges` is read from the imports of TypeScript, JavaScript and the scripts of Svelte files (needs the TypeScript 5 compiler API as `typescript` or, beside a newer typescript, the alias `typescript-5`; it is not a declared peer, so a repository on TypeScript 7 installs the alias), Python (`lang: "py"`, `sourceRoots`) and Kotlin (`lang: "kt"`), including `new Worker`, `new URL(.., import.meta.url)` and template imports. `entry` is the module's door (a name, a list, or `"*"`), `acyclic` finds module cycles, `edgesOnly` asks for no door, `closed` makes an import out of every module a breach, `onlyFrom` limits the importers, `hard` takes no exception at all. `workspaces: true` (off unless a rule names it) also reads an import of the repository's own package by its package.json name (`@scope/pkg`, `@scope/pkg/sub`) through that package's `exports` (or `main`), as Node resolves it: what a package exports is its door, so the edges and cycles of a monorepo whose packages import each other by name are seen. Breaches are named by file and target, never pooled.
- **A ratchet against the parent commit.** A raise of a known exception, a removed or renamed rule, a lower bar (`max`, an excluded file, a lost `hard`), a widened dependency, a changed door, a dropped module or a changed `guard` is red unless `arch.decisions.json` gains, in the same commit, a decision with who, when, message and its `ceilings` (`<rule>:max`, `<rule>:import:<from>><to>`, `<rule>:entry:<dir>`, `<rule>:module:<dir>`, `<rule>:exclude:<file>`, `guard`) or `removes`. A decision of an earlier commit never licenses a later change, and none can be altered or dropped. `--adopt <rule>` names a new rule's breaches once; a new rule's keys must equal today's breaches.
- **A baseline that grows only by a dated decision (0.13.0, Cut row 1868).** A count of a rule that stands may grow, or a new key of that rule appear, only when `arch.decisions.json` gains in the same commit a decision whose `ceilings` names the key with at least that count, and says `why` (words) and `until` (the day the exception goes, `2026-12-01`). A move needs none: a key that left in the change lends its count to one new key of the same rule with the same or a lower count (a split file, a rename past git's). A decision whose `until` has passed is red while a key it names still stands in the baseline; a later decision for the key carries it, and once the key is gone (`--lower`) the decision is history. `--init` writes a first baseline only, in the CLI as in the guard; an existing one only shrinks.
- **Code that reads as a story (0.14.0, Cut row 1873).** Three kinds in `story.mjs`. `eslint` `{rule, options?}` counts one ESLint rule per file (`max-lines-per-function`, `sonarjs/cognitive-complexity`, `max-depth`, `max-params`, `@typescript-eslint/no-use-before-define`, ...), each hit naming its function; every `eslint` rule of a config runs in one pass over `.js`, `.mjs`, `.cjs`, `.ts`, `.tsx`, `.mts` and `.cts`, with inline disables ignored, and a file ESLint cannot read or skips stops the run. ESLint, `typescript-eslint` and `eslint-plugin-<name>` come from the repository's devDependencies (on TypeScript 7 the parser is handed `typescript-5`); `ARCH_CACHE_DIR` keeps ESLint's cache by content. `first-line` asks line 1 (after a shebang) to be a one-line comment on what the file is for. `story-order` names each private helper (a function declaration, or a const holding a function) above the last inline export of a file (`export function`, `export const`), to move below it; a file that exports by a list is left alone, its list being its table of contents. Each starts with today's breaches (`--adopt`), which only shrink. A decision may also name what `waits` (`{"waits": {"python": "why"}, "until": "2026-12-01"}`), red after its until unless a later decision names it again.
- **Stepdown, touched files, --fix and exceptions (0.15.0, Cut row 1873).**
  - `stepdown`: a function stands below every function of its file that calls it. Exempt are recursion, functions that call each other, a helper's call of an export (story-order puts exports first) and a function that top-level code also uses (a test fixture, a script's main line).
  - `stepdown-order`: names the functions that are out of the order their first calls are read in, depth first.
  - JS and TS are read with the TypeScript AST; Python with the repository's `python3` and its `ast`, in one run.
  - `story-order` and `first-line` read Python too. `first-line` accepts a header whose first line says what the file is for.
  - A rule with `report: true` is counted but is never red and never enters the baseline (`--adopt` refuses it).
  - A rule with `failsFrom: "YYYY-MM-DD"` (0.18.0) tells a breach before that day, printed as `(told; red from ...)`, and is red from it; its counts stand
    in the baseline from the first day (`--adopt` takes them), so a new kind is read against its first hits before it stops a push. `check()` returns the
    told lines as `told`; `--today` sets the day.
  - The `eslint` kind takes three more options. `exported: true` keeps only breaches on a top-level exported function's head (max-params for a file's API). `skip` lists functions, by name or `/regex/`, that hold no logic of their own (feature, describe, a `/^create[A-Z]/` factory whose inner functions are counted each). `loops: N` lets max-depth reach N where a loop is part of the nesting (0.15.1).
  - Story-order leaves a const helper that top-level code runs at load, and a Python def that module code uses at load (0.15.1, Huset's trial).
  - `eslint: {from: "tools/lint"}` in arch.config.json loads ESLint and its plugins from that folder's own install (a repository on TypeScript 7 keeps TypeScript 5 there for typescript-eslint); not installed there, the run stops with `npm ci --prefix <from>`, and export.mjs links the folder's node_modules into its export (0.15.5).
  - A decision's `decided: {what: how}` ends what waited, so a wait that was decided is not red after its until (0.15.5).
  - `exceptions`: each eslint-disable, `@ts-ignore`, `@ts-expect-error` and `@ts-nocheck` must name what it turns off and carry `lint-allow <rule>: why; until YYYY-MM-DD` on its line or the line above. A passed until is red. A file in `configs` that turns a rule off needs a decision `{"allows": {"eslint.config.mjs:rule": "why"}, "until": ...}`.
  - A story rule carries its catalog entry: `what`, `why` (1-2 lines) and `example: {without, with}`. The guard's policy requires them.
  - `touched: {rules, files, exclude?, changedLines, wholeFile}` in arch.config.json makes each file a push touches hold the named rules (story-order, stepdown, first-line), whatever its baseline. A line the push writes stays within `changedLines`, and no line of a touched file is over `wholeFile`. A commit message with `tidy-later: <row>` turns the faults into a notice for that push. By hand, the touched files are the work tree's changes against HEAD. A deploy (`export.mjs --commit`) and anything run with `ARCH_TOUCHED=off`, such as Cut's release, hold no touched files: each push was held at its own (0.15.4). A line the push only moves within its file is not written (0.15.2): each added line whose text a removed line of the same file had counts as a move, one removed line per move, so a --fix tidy keeps its long lines until someone writes them.
  - A split lands low and is a move with a name (0.19.0, Cut push-protocol-15 and -16, `guard/split.mjs`). For a `max-lines` rule with `split: {from, lands}`, a push that moves code out of a file over `from` (the file shrinks and another file of the push grows in lines of code) leaves it at `lands` or under, the rule's `fix` saying the steps; a push that only deletes is free, and a touched file from `from` gets a note, not a fault. `touched.newNames: {pattern, flags?, files?, fix}` is what the name of a file the push adds must match (`files` defaults to touched's). Both read the push's base, so a release (`ARCH_TOUCHED=off`) holds neither, and tidy-later only tells them.
  - `--fix [files]` moves whole top-level functions, with the comments above them, for story-order and stepdown. It changes no line and never moves a function past code that runs it at load. A file that would not keep the same lines, parse as before, break no more and run no more functions at load before they are defined is left as it was. Since 0.15.3 a function lands right below its last caller; 0.15.0 to 0.15.2 put it one block further, past load-time code when that came next (the gateway's scripts/catalog.mjs).
- **Sandboxes and doors (0.12.0).** Four kinds read the modules of the `modules` rule their `of` names. `sandbox` loads each module's `example` in a bare node with no page stubbed (no document, no window): a load that throws is a breach, and so is each file it loads outside the module, the modules its declared imports reach and their `rootImports` (a package, a folder the rule leaves out and node's own modules are not outside); `seconds` bounds a load (20). `lazy-imports` counts each module's `import()` calls, whose computed paths the cycle guard cannot follow; its `skip` (a regex, 0.12.1) leaves files out, such as tests, which no module imports, and changes only by a decision. `door-names` counts the names a door exports (`export *` followed, its default not; an `export * as X` of a file it can read as every name that file lets out, its default too, since 0.17.1) where they pass `max`. `other-doors` names each door beside a module's first, and `*`: it stands only by a decision in `arch.decisions.json` whose `doors` gives it with when it goes (`{"doors": {"<module>/<file>": "<when it goes>"}}`), never by the baseline. The first three start with today's counts (`--adopt`), which only shrink.
- **A cache of imports (0.10.1).** With `ARCH_CACHE_DIR` set to a folder, the specifiers each file names are kept by the file's content (sha256 of its text and name's extensions, per TypeScript version): a run after a rebase parses again only the changed files, and the rules of a repository share one parse. Same counts as without it; an unreadable cache is no cache; nothing is kept when the variable is unset.
- **The guard of the guard** (`policy.mjs`): `arch.config.json` names `guard: {wrapper, lint, docsOnly?, branches?}`; `npm run lint` must run that wrapper and the wrapper must still check the hash.
- **`export.mjs`** lints a commit in an export of it: as a pre-push hook (`node node_modules/@v1d/arch-check/guard/export.mjs`; a push to a branch that `guard.branches` names, a regex of branch names, `master|main` by default, 0.11.1) or for a deploy (`--commit <sha>`; a commit from before the guard is a rollback and is not checked). The lint there gets 240 s before it is stopped (0.17.3; 120 s until 0.17.2).

Exit codes of the wrapper: 0 holds, 1 a breach, 2 a rule that cannot run or a package that is not the pinned one.
