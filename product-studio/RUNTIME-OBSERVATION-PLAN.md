# Product Studio: optional runtime observation and release plan

Status: implementation proposal, not a shipped capability. Prepared 2026-09-23.

Reviewed CircleKit source: `4d0875371207688d6036564bd45e799ab810355e`.

This document is the implementation handoff. It specifies the recommended design, alternatives, boundaries, delivery slices and owner-local acceptance criteria. It does not authorize a release, license change, deployment, product execution or GitHub CI. No tests, builds, syntax checks, emulators or applications were run while preparing it.

## 1. Decision in one page

Build **optional, local, read-only runtime observation** over the model Studio already understands. Reuse the existing graph, finite evaluators, source navigation and trace inspection. Do not build a second IDE, general debugger, orchestration system or observability backend.

The developer-facing outcome is:

> Declare the boundary once. See its structure, the calls that actually ran, and where observed results disagree with the declaration.

The first release observes three existing event families: named port calls, decision evaluations and machine evaluations. A machine's **applied state change** is a stronger, separately identified observation, collected only at the real state owner. Network connectivity, matching IDs and passing declaration laws must never imply that an application is correct.

Recommended decisions:

| Decision | Choice | Reason |
|---|---|---|
| Product boundary | Observation, not control | Supplies new runtime evidence without acquiring authority to mutate apps. |
| Transport | Outbound WebSocket from a debug adapter to an explicitly enabled Studio receiver | Ordered, bidirectional delivery acknowledgements without a server on the phone. |
| Network scope | Loopback; Android through explicitly selected ADB reverse forwarding | No discovery service, LAN exposure, accounts or cloud relay. |
| Runtime integration | Shared transport-free observation hooks plus optional adapters | Business code does not hand-write events or depend on the Studio viewer. |
| Model identity | Generated by the product's build and embedded with that build | A stale installed app cannot borrow the current checkout's identity at connection time. |
| Evidence format | Read trace v1; introduce a small explicit trace v2 for live capture semantics | v1 cannot honestly represent trailing loss or evaluation versus applied state. |
| UI | A live session overlay on the existing graph/Trace views | No second canvas, layout engine or runtime-specific model. |
| Agent interface | Bounded JSON reads from an already-running Studio; existing offline commands remain unchanged | Useful to coding agents without MCP, an embedded LLM or permission to execute commands. |
| Release scope | Node reference app, one local-web integration and one Android pilot | Demonstrates portability without promising universal framework support. |
| Deferred | Arbitrary snapshots, control, breakpoints, remote production access, OTLP/DAP adapters | None is required to demonstrate the core value. |

These are this plan's recommendations. They are not retroactive claims about decisions already approved by the owner.

### Corrections to the earlier concept

1. Live attach is **not just putting today's recorder on a socket**. Existing Node and generated Kotlin sinks perform file I/O; the live hot path needs different delivery and failure behavior.
2. The generated Kotlin `declaredNext` hook observes a selected result, not the caller subsequently committing that state. Label it accordingly.
3. A `snapshot` in the first release means an immutable snapshot of **Studio's captured observations**, not arbitrary access to application memory.
4. Reuse one listening port by default. The previously discussed separate 4318 port is not necessary. Keep Studio's existing 4317 default, with the actual port printed when overridden.
5. REST is a viable alternative, not inherently the wrong abstraction. WebSocket wins here because it avoids separate continuous delivery and acknowledgement paths.
6. Existing numeric enthusiasm or adoption estimates are not measurements and must not become release evidence.

## 3. Alternatives considered

| Alternative | Good fit | Why not the primary first-release path |
|---|---|---|
| Explicit trace files only | Offline debugging, bug attachments, minimum runtime integration | Keep it. It does not provide immediate feedback while interacting with an app. |
| Bounded HTTP batch POST | One-way export, constrained clients, easy request-level tooling | Technically sound. It would require a separate policy for ongoing status/acknowledgements; do not implement two ingress transports initially. |
| Server-Sent Events | Studio pushing observations to its own viewer | Does not by itself solve app-to-Studio ingress. A second transport is unnecessary for the first vertical slice. |
| Outbound WebSocket | An opt-in continuous local inspection session | Selected. Must explicitly solve auth, backpressure, lifecycle and disconnect semantics. |
| App-hosted HTTP/WS server | Existing apps that already expose a trusted diagnostic server | Makes device discovery, listening ports and access control the product's problem. Not the default. |
| OTLP/OpenTelemetry | Existing telemetry infrastructure and later production investigations | OTLP standardizes telemetry export over HTTP/gRPC; it does not provide our model/evaluation identity contract. Later adapter, not a mandatory collector stack. [E3] |
| Debug Adapter Protocol | Breakpoints, stacks, variables and integration with language debuggers | DAP is an IDE/debugger protocol. Studio should complement those tools, not implement their responsibilities. [E4] |
| Development-server proxy | A local-web adapter whose browser cannot connect directly under its origin/security policy | A bounded adapter option, not a Studio-wide relaxation of browser security. Defer unless the supported browser matrix needs it. |

No numerical complexity scores are assigned: implementation costs have not been measured.

## 4. Non-negotiable scope and DX budget

### First-release scope

Read-only observation, pairing, session selection, exact identity checks, bounded capture, source navigation, finite-result comparisons, freeze/export/reopen, and concise agent-readable inspection.

No automatic app startup, generator runs, dependency installs or ADB changes when simply opening Studio. The existing explicit `record -- TEST_COMMAND` remains an intentionally different owner-invoked operation.

### Boilerplate budget

- Zero handwritten JSON trace envelopes, hashes or entity-key encodings in product business logic.
- Zero new WHAT/WHY copies, debug annotations or `debuggable` fields per service/port.
- One opt-in build/dev integration and one bootstrap per runtime process at most.
- Standard ProductSpec calls are captured automatically through the selected development entry.
- Applied-state observation may require one reusable hook at an existing state-owner abstraction. Do not scatter one hook per transition.
- Dynamic instance identity requires one binding at instance construction only where the product actually has multiple runtime instances.
- No runtime network dependency on the viewer package. Platform transport adapters are development-only dependencies.

Zero integration is not a promise. A program with no ProductSpec declarations or observation hooks cannot have its architecture reliably reconstructed by Studio. Start with one boundary/table/machine in an existing app; no whole-application migration is required.

### Mermaid boundary

The graph is a projection of compiled ProductSpec structure, not another diagram source. Use the existing graph renderer and identity index for architecture, finite logic and live overlays. A developer should not maintain a Mermaid graph of structure already declared here.

Do not delete existing Mermaid exporters or require a new layout/diagram DSL. Static exports remain useful for README/PR communication. Studio does not replace Mermaid for brainstorming or systems outside its declared scope. A future SVG export should use the same graph projection, not a second graph model; it is not a release prerequisite.

## 5. Developer journeys

All new commands and API names in this document are **proposed interfaces**, not commands available in the reviewed release.

### A. Try the public example without a phone

Provide one self-contained example: an ordinary job/request machine with a decision table and named input/output bindings. The example runs real ProductSpec calls in a local process using deterministic, fake business data. It is a demo app, not evidence about SKYVW or a physical device.

From its documented checkout:

```text
Terminal 1: v1d-studio --live
Terminal 2: npm run dev
Browser:    choose the waiting producer and approve pairing
```

The example's own `npm run dev` starts the app; Studio never does so implicitly. The developer clicks an action in the example, sees a captured evaluation, follows its exact source, freezes a capture and reopens it. Demonstrate an explicit disagreement using a deliberately incorrect demo state-owner implementation, not a secretly fabricated live event.

### B. Local web application

Provide one optional adapter, initially for the local Vite development path already used by the ecosystem. A prospective configuration shape is:

```ts
// Proposed API. Development tooling only.
plugins: [runtimeObservation({ workspace: '..' })]
```

The adapter reads the selected workspace and generated identity descriptor. It selects the browser-safe observed ProductSpec entry, installs one sink and creates one connection for the page's runtime instance. It refuses ambiguous multi-project selection instead of guessing.

The developer approves the exact local origin in Studio and uses a one-time pairing ticket in the application's development overlay. Do not put credentials in `VITE_*`, committed environment files, query strings, emitted JS or source maps. Keep pairing in memory; reload/restart can require pairing again.

The adapter is inert outside the dev-server path. Handle browser page, SSR process and worker as separate producers. HMR must dispose old listeners/sinks/sockets. A model-affecting HMR change cannot silently keep the previous model identity: require a new valid descriptor and new capture, or report `source/model stale` and suspend correlation. Never auto-run generation from the viewer.

Do not promise production HTTPS websites can contact a local `ws://` endpoint across all browsers. Test CSP, mixed-content and local-network access rules on named browser versions. Prefer local development origins in this release. Chrome's local-network policy is evolving; an older exception is not a compatibility guarantee. [E5, E6]

### C. Android emulator or USB-connected phone

Install the transport adapter only for the debug build, with a small transport-free hook surface where generated code needs it. The product's existing generator emits build identity and registers its generated observation hooks once.

Daily connection:

```bash
# Existing Android tooling, executed explicitly by the developer.
adb -s SERIAL reverse tcp:4317 tcp:4317
```

Use the actual Studio port. The official ADB path supports device/emulator access to a host-local server. It is forwarding, not authentication. [E1]

Pair from the debug app's existing developer screen: paste a one-time high-entropy ticket, then tap Connect. A desktop helper may transfer the ticket through an explicitly selected, authorized ADB device to an app-private debug-only entry, but that convenience is not required for v1. Do not introduce an exported production intent/deep link, auto-select the first device, print credentials in shell logs, or bake a token into the APK.

Use `debugImplementation`/debug source sets for transport and UI. The relevant module's compile-time debug guard gates emitted calls. Host JVM test recording and Android live observation are separate sink selections; Android must not depend on a JVM test runner's environment variable. Network-security configuration must be narrowly scoped to the debug build and loopback destination. Do not globally weaken production cleartext/TLS policy; `debug-overrides` for CAs is not a generic cleartext exemption. [E2, E7]

Respect app/process lifecycle, doze and background restrictions. Do not add a wake lock or foreground service just to keep Studio connected. Disconnection must not affect recording, sensors, navigation or other app behavior. First physical-device verification is a desk/debug exercise, not a jump or other safety-critical activity.

### D. Coding agent investigating a problem

The agent reads the same immutable capture the human sees. Proposed examples:

```bash
v1d-studio live --json
v1d-studio live --session SESSION_ID --json --max 50
v1d-studio live --session SESSION_ID --freeze --output local-capture.studio-trace.json
```

`live` connects only to an explicitly enabled, already-running local Studio instance. It never launches the app, claims a device, pairs without owner approval, runs tests or acquires control capabilities. If more than one Studio instance or producer matches, return candidates and require explicit selection.

The JSON contains capture/model identity, capture cutoff, observation phases, dropped/unknown counts, comparisons and source locations. Existing offline `plan`, `inspect`, `trace` and `converge` keep their current behavior; do not make their output silently depend on whichever live phone happened to connect.

## 6. Architecture and responsibility map

```text
Product-owned declarations + existing build
                 |
                 +--> compiled model / Studio bundle
                 +--> embedded runtime identity descriptor
                 +--> optional generated hook registration

Actual ProductSpec calls / native state owner
                 |
       transport-free observation seam
                 |
       bounded, non-throwing capture queue
                 |
        debug-only platform adapter
                 |
          authenticated local WS
                 |
     session + loss + identity validation
                 |
 existing model index and finite comparisons
                 |
     existing graph / Trace / JSON reads
                 |
          explicit trace v2 export
```

### Code ownership

| Layer | Existing location to start from | Planned responsibility |
|---|---|---|
| Public evaluation hooks | `product-spec/src/studio-trace.ts`, root conditional exports | Factor observation away from file output; retain the normal pure entry. |
| Common raw observation model | ProductSpec observation subpath, transport-free | Typed events using declared IDs, not Studio UI entities. No fs, sockets, timers, viewer imports or global process assumptions. |
| Test-file adapter | Existing `studio-trace` path and `product-studio/lib/record.mjs` | Continue explicit owner test capture. Share normalization, not live error behavior. |
| Kotlin evaluation hooks | `product-emit/src/core/emit-machine-kotlin.ts`, `emit-decision-table-kotlin.ts`, `emit-studio-trace-kotlin.ts` | Generate typed calls at actual evaluation boundaries and a process-level sink connection, not duplicated networking/JSON writers per emitted class. |
| Optional transport clients | Proposed small `@v1d/runtime-observation` package with browser/node/dev-adapter subpaths; Android debug adapter | Pairing, queueing, serialization and lifecycle. Peer/use the product's kernel, never install a second evaluator. Names need release-owner confirmation before publishing. |
| Shared normalization | Extract from `record.mjs:eventFor` | One mapping from raw declared IDs to Studio entity keys for file and live paths. Preserve unknown/malformed distinctions. |
| Receiver | A small module composed into `product-studio/server.mjs` | Upgrade auth, sessions, bounds, lifecycle. Not a monolithic expansion of `workspaces.mjs`. |
| Trace format | `product-studio/lib/trace.mjs` and adjacent schema/fixtures | v1 compatibility and explicit v2 lifecycle/observation semantics. |
| Comparisons | Existing workspace/finite evaluation path | Evaluate with the exact selected product kernel; no app code execution. |
| UI | Existing `public/app.js`, graph and trace helpers | Session/capture overlay; no duplicate graph or full editor. |

The runtime package must not import Studio's Node-oriented `./trace` implementation into browsers. The shared wire model is a small serialization contract, not a new domain DSL. Publish one canonical wire schema and common golden vectors; any platform types/decoders must agree with those vectors rather than inventing their own semantics.

## 7. Identity: bind evidence to the build that produced it

### Required handshake identity

- `productId`: the compiled product identity, not a friendly workspace alias. For example, a workspace alias and its artifact product ID can differ.
- `identity`: exactly one of the existing `modelDigest` or `artifactSha256` mechanisms, generated by the product's trusted build from the corresponding actual output.
- `productSpecVersion`: the actual producer kernel version used by that build.
- `captureId`: fresh opaque random ID per connection/capture segment.
- `buildId`: optional diagnostic build label, never an alternative to model identity.
- `scope`: the declared observation families/facets this adapter can capture. This is advertised instrumentation scope, not a claim that every call was observed.

For JS with an inspection bundle, consume its existing model identity. For a native raw ProductIr path, the product build hashes the exact artifact bytes and emits the resulting constant alongside generated code. Do not reimplement the model hash in Kotlin. The runtime descriptor is output from the same owner build, not a hand-maintained third specification.

A descriptor must not be computed by asking Studio which hash it currently wants. It must not be read from a changing checkout after an older app has already loaded. Exclude the descriptor itself from the source closure used to compute it, so generation has no self-referential hash cycle.

Where source is hot-reloaded, the adapter must distinguish active executable source identity from a newly written descriptor. If it cannot establish the relationship, it disables correlation until a coherent rebuild/reload.

### Matching and trust

| Situation | Receiver/UI behavior |
|---|---|
| Product and exact model/artifact match; exact evaluator available | Accept a correlated session; comparisons use that evaluator. |
| Same product name, different digest | Reject event attachment; show only bounded mismatch metadata. Ask to open the matching build, never relabel the producer. |
| Several workspaces contain the same product/digest | Owner selects the workspace before attachment. No arbitrary first match. |
| Kernel unavailable or mismatched | Inspection may remain available; comparisons are `unavailable`, not successful. |
| Local source has changed but loaded compiled model still matches runtime | Model correlation may remain valid; source navigation/patching must show stale source independently. |
| Producer repeats or changes immutable identity during a session | End that capture with a named protocol error; require a new handshake. |

A digest match is not binary attestation. A buggy or malicious adapter can report false identity or outcomes. Display `producer-reported, identity-correlated observation`, not cryptographically proven runtime truth. Likewise, a matching native transition does not prove sensor accuracy, thread safety, effect completion or correct business requirements.

## 8. Capture the right observation, not an attractive approximation

### Three initial event families

| Family | Default phase | What may be asserted | What must not be inferred |
|---|---|---|---|
| `decision` | `evaluated` | The selected ProductSpec evaluation returned this cell/result for these supplied finite facts. | The consumer applied the result or an external effect succeeded. |
| `transition` | `evaluated` | `step`/`declaredNext` selected this result for the supplied state/input/guards. | The running machine's state changed. |
| `transition` | `applied`, only at a real owner hook | The instrumented owner reports committing the observed state change. | Durable persistence, device correctness or observation of every transition. |
| `port` | `returned` | The named function returned to its caller. | A returned Promise fulfilled, the peer received data, or a binding/effect succeeded end-to-end. |

No generic `effect` or arbitrary `state` payload stream in v1. The existing trace event vocabulary may contain more kinds, but their presence does not establish automatic capture support.

### Capturing applied state elegantly

Capture evaluation automatically. Where an actual state owner exists, attach one development observer to its commit/update boundary. Generate a typed reference to its declared machine; avoid stringly typed calls scattered across every case.

The hook records actual before/input/after and the supplied guards. It must not recompute `after` from ProductSpec and then call that an observation. An ignored, clamped or changed evaluation result must remain detectable.

A pure function used only to preview a possible transition must never move the live-state indicator. Without an applied hook, the UI says `Last evaluated transition`; it does not show an asserted current state. A latest applied record is still `Last observed state`, with age and disconnect status, not a guarantee that nothing changed since.

### Instance, ordering and wrapper correctness

When several objects share one machine declaration, generate or bind an opaque instance ID at their state owner. Keep separate lanes by capture, facet and instance. Without an instance ID, show individual evaluations without constructing a continuous machine path. Never stitch all uses of a shared machine into one invented timeline.

Preserve receiver/`this`, synchronous return value, thrown application errors, stable wrapper identity where callers rely on it, and Promise identity. No extra awaits or swallowed application errors. Observer failures are caught only around observation; they must not mask the application's own exception. Do not evaluate the declaration twice just to capture it.

Selecting an observed public entry does not automatically intercept every internal/direct-subpath import. Report supported hook scope explicitly; audit real consumer imports. Do not claim whole-program instrumentation, instrument compiler enumeration as app behavior, or globally enable observation in build processes. Product builds and imported library kernels remain independently owned.

## 9. Protocol v1: small, bounded, no app-control messages

Receiver path: `ws://127.0.0.1:<actual-studio-port>/runtime/v1`. Enabled only by explicit `--live`; ordinary Studio does not register it. Use a maintained WS implementation rather than handwritten WebSocket framing. Select and lock an appropriate supported version during implementation; none is selected or installed by this plan.

Use UTF-8 JSON messages and the subprotocol `v1d-runtime.v1`. Protocol version and archived trace version are separate: a live connection is not itself a trace file.

### Message vocabulary

| Message | Direction | Required meaning |
|---|---|---|
| `hello` | Producer to Studio | Authenticate; declare immutable build identity, fresh capture ID and supported capture scope. No event data before acceptance. |
| `welcome` | Studio to producer | Confirm authorized session and bounds; issue a scoped reconnect credential. Does not supply/rewrite the producer's model identity. |
| `batch` | Producer to Studio | Ordered raw observations, declared dropped ranges and a final sequence watermark `through`. An empty batch may publish a watermark. |
| `ack` | Studio to producer | Highest validated watermark retained/processed by the in-memory receiver. Not a durability or proof-of-correctness acknowledgement. |
| `end` | Producer to Studio | Final watermark/loss declaration after capture is disabled; clean completion only after receiver acknowledgement. |
| `error` | Either direction | Bounded machine-readable code and safe message; fatal protocol errors close the connection. |

Use standard WS ping/pong for connection liveness. A producer emits an empty watermark batch when necessary to report trailing producer-side loss. Do not add generic RPC, `eval`, shell, file access, app pause/resume or input invocation messages.

### Illustrative handshake, not a real captured build

```json
{
  "type": "hello",
  "protocol": 1,
  "ticket": "ONE_TIME_SECRET_NOT_FOR_LOGS",
  "productId": "demo.request",
  "identity": {
    "modelDigest": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  },
  "productSpecVersion": "0.3.67",
  "captureId": "opaque-new-capture",
  "buildId": "optional-owner-build-label",
  "scope": {
    "events": ["decision", "transition", "port"],
    "facets": ["demo.request"],
    "appliedTransitions": false
  }
}
```

The version in this example is illustrative, not a required consumer upgrade. Unknown protocol major versions are refused. New optional capabilities require explicit negotiation; the receiver must not silently ignore unknown core message fields. Keep missing/unknown event facts distinct from malformed protocol messages.

### Sequence and delivery algorithm

1. Start capture only after `welcome`. No secret pre-pairing history is uploaded. Assign sequence 0 to the first attempted captured event, then increase monotonically, including events dropped by the observation queue.
2. Stamp each event with producer monotonic elapsed milliseconds. Assign sequence and timestamp consistently at the capture queue's serialization boundary. Do not sort later by wall clock or mix clocks from different processes.
3. Keep at most one unacknowledged batch per connection in v1. Each batch covers the next contiguous sequence interval ending at `through`, partitioned into events and explicit dropped ranges. It may contain only losses.
4. Validate the entire bounded batch before committing its cursor. Every covered sequence appears exactly once as an event or a loss. Reject overlap, duplicate sequence, backwards time or unexplained jumps. Preserve named loss reasons.
5. `ack.through` advances monotonically. A batch larger than the negotiated byte/event limits is refused. The SDK splits batches before sending.
6. On disconnect, keep the received segment marked interrupted with unknown tail. Do not infer that all produced events arrived from the last successful socket write.
7. Reconnect using the scoped credential, but start a fresh capture ID and sequence space. No durable replay/resume protocol in v1. Link segments visually as reconnects without asserting uninterrupted history.
8. On owner Stop, disable capture first, flush its bounded queue/loss records and send `end`. If flushing or acknowledgement times out, retain an interrupted segment. Never block app shutdown waiting for Studio.

Use a bounded control slot so queue overflow cannot prevent reporting the dropped-event watermark. If detailed loss ranges themselves overflow, stop that capture as incomplete rather than inventing exact ranges.

## 10. Trace v2: reuse the data model, preserve uncertainty

The current v1 decoder explicitly rejects trailing loss and has no observation-phase/instance fields. A sidecar with critical semantics would be easily separated from a trace. Silently discarding these fields on save would create false confidence. Therefore introduce **trace version 2**, while retaining v1 reads unchanged.

Reuse existing event kinds, entity-key construction, finite logic payloads and source/model identity. The small additions are:

- Per-event observation metadata: `phase` and optional opaque `instanceId`. Allowed phases are constrained by event kind as in section 8.
- Capture metadata: transport, advertised instrumentation scope, capture cutoff/watermark and ending state (`open`, `clean`, `interrupted`). Optional producer build label is descriptive only.
- Loss semantics that allow ordered missing intervals through the last producer-advertised watermark, including trailing losses. An interrupted connection explicitly leaves the tail beyond that watermark unknown.

Keep the existing top-level provenance categories: `recorded`, `test-run`, `synthetic`. Live adapters supply `recorded` explicitly. Do not apply v1's virtual/test-run defaults to live imports. Identity, provenance and observation phase answer different questions and must remain separate fields.

For v2 validation, `events` plus loss intervals must cover the retained declared interval exactly; `droppedBefore` describes evicted prefix data. A clean ending needs a final acknowledged producer watermark. `open` snapshots describe a cutoff, not a finished execution. An unknown tail must never be converted to zero loss.

Opening v1 preserves its original meaning. Its transition events have unspecified application-commit semantics; do not upgrade them to `applied`. Continue inspecting their recorded finite-result claims, labelled legacy/unspecified observation semantics.

Update file decoding, CLI, browser import/export, paging, causality and convergence readers in one compatibility slice. Older readers should refuse v2 explicitly, not partially accept it. Protocol schema/golden vectors must cover both versions. Do not change ProductIr merely to store transport/session metadata.

### Freeze, save and reopen

Freeze captures an immutable prefix/cutoff for inspection while the app continues. Pause in Studio pauses the viewer cursor, never the app. Export requires an explicit user action and a separate destination, with atomic write and path/symlink checks consistent with existing bounded exports.

The exported trace is one file containing its necessary evidence semantics. It still requires the matching model/bundle to interpret it; do not claim a trace alone reconstructs an unknown app. Do not automatically package product source or silently rehash a redacted model. Missing model leads to `Open the matching bundle`, not a network download.

Default destination is a user-selected local capture location, not the conventional owner-test report that `record` writes. Never overwrite test evidence with a live session. Raw incoming messages, credentials and absolute private source paths must not be written to logs or included in an export.

## 11. Security and privacy contract

### Trust boundaries

Threats considered: hostile browser pages contacting localhost, malformed producers, another local app using the forwarded port, compromised/buggy adapters, data leakage in traces, stale or mismatched models and an agent treating producer text as instructions. A compromised host OS or same-user process with access to all developer files is not solved by this bridge. Model identity is not attestation.

### Pairing and authorization

- No unauthenticated model/source enumeration through `/runtime/v1`.
- Generate a 256-bit random one-time ticket after an explicit owner action. Proposed ticket lifetime: 120 seconds. Consume it atomically on successful authentication; rate-limit failed attempts.
- Bind the ticket to the selected workspace/product, producer type and, for browsers, one exact permitted development Origin. The product supplies its build identity separately; a mismatch is visible and never rewritten.
- Authenticate in the first bounded message, not a URL/query string or cookie. Unauthenticated sockets get a 5-second deadline and a strict connection/message cap.
- Issue a separate reconnect credential limited to this live receiver, product and producer type. Keep it in memory, expire it after at most 8 hours or server stop, and revoke it on Disconnect/Revoke. It cannot read Studio sources, create drafts or call ordinary HTTP APIs.
- Native producers may omit Origin only with a native-scoped ticket. Browser producers require the exact approved Origin; reject missing, `null`, wildcard and lookalike Origins. Origin is an additional browser defense, never a substitute for credentials.
- Keep existing UI HTTP Host/Origin/token protections unchanged. The runtime WS route is the only deliberate cross-origin exception. Review its Upgrade path independently; do not globally disable `sec-fetch-site` or CORS checks to make a browser example work.
- Use the existing port and literal loopback host by default. Never bind `0.0.0.0`. Cleartext WS is limited to this explicitly authorized local debug/ADB topology; production or LAN access would require a separate secure design. Do not add a production fallback.

OWASP identifies independent WS authentication, exact origin validation, bounded input, backpressure and avoiding token logging as important defenses. The numerical lifetimes above are proposed project policy, not values mandated by OWASP. [E8]

### Data minimization

Default port observations carry identity/timing only, not argument/return payloads. Machine inputs carry declared event identity and boolean guards, not sensor samples. Decision facts/results are restricted to bounded, model-declared finite values needed for comparison. Arbitrary objects, free text and dynamically supplied strings are excluded by default; numeric/raw-value capture requires a narrowly reviewed product policy, not `JSON.stringify(appState)`.

Never automatically capture coordinates, audio, prompts, access tokens, account IDs, URLs containing secrets or user records. Redaction occurs before queueing/transmission; server validation is a second boundary. If necessary facts are excluded, show `not comparable: facts unavailable/redacted`, never substitute declared values or zeroes to obtain green status.

Opaque instance labels are process-local, not persistent device/account identifiers. Default capture is memory-only and off until pairing. A running app must show a visible development indicator and a stop/revoke action. Disable compression initially; validate message size/depth and forbidden object keys. Escape every producer-supplied display string.

## 12. Performance, overload and lifecycle

These are initial engineering budgets to implement and measure, not achieved benchmark results. Tighten them based on actual Node/browser/Android observations before release; document any change rather than silently lifting every limit.

| Boundary | Proposed first-release budget/policy |
|---|---|
| Live producer sessions | 4 active; isolated per-session buffers; reject additional sessions explicitly. |
| Unauthenticated sockets | 4 total, 5-second handshake deadline. |
| Individual raw observation | 8 KiB serialized maximum; fixed nesting/key/string limits. |
| Batch | At most 128 events and 64 KiB, whichever is reached first. |
| Flush cadence | Up to 20 batches/second, or earlier within the same rate budget when a batch is full. |
| Producer queue | At most 2,048 events and 1 MiB; whichever limit is reached first. Drop new observations, record their sequence ranges, never block the producer. |
| Transport backlog | One unacknowledged batch; 256 KiB maximum adapter/socket buffered bytes; timeout rather than unbounded buffering. |
| Studio retention | At most 20,000 events and 8 MB per session; also enforce a 32 MB aggregate event-data cap. These are data budgets, not a promise of equivalent process RSS. |
| Comparison work | Bounded incremental backlog; when exhausted, mark unprocessed results unavailable. Never claim every retained event was compared. |
| UI refresh | At most 10 visual updates/second; do not re-layout the graph per event. Hidden tabs pause rendering. |
| Connection liveness | Ping every 15 seconds; mark disconnected after 45 seconds without response. A quiet app is not disconnected merely because it emits no business events. |
| Reconnect | Bounded exponential backoff with jitter, capped at 10 seconds; stop on revocation/protocol mismatch. |

Capture must be non-throwing and non-blocking with respect to network/file delivery. Bounded allocation/copying still costs CPU; do not claim zero overhead. No payload serialization or lock held across I/O on UI, sensor, audio or state-owner threads. Observer failures disable observation and surface a diagnostic without changing app outcomes.

Measurements required on named hardware: disabled build versus enabled-but-disconnected versus connected normal load versus receiver stalled. Record application latency, CPU/allocation change, dropped observations and observer queue/heap bounds. Proposed pilot target: no more than 5% regression in the selected application's p95 operation latency under ordinary capture. This is a release target, not proof of real-time suitability or a universal performance guarantee.

At HMR, Activity recreation, process restart or server restart, avoid duplicate sinks and reconnect storms. Register/dispose once per actual process/realm, not once per screen. Preserve independent session clocks; no total distributed order or causality inferred from timestamps. Do not keep a mobile app awake solely for telemetry.

## 13. UI and agent behavior

### Reuse the existing UI

Add one session selector and a live status strip to existing views. Retain graph camera, selection, keyboard behavior and source links. A live overlay can show port activity and evaluated/applied finite logic with distinct styles and text, not color alone. Do not draw an observed binding merely because its endpoints happened to be active.

Opening a large graph starts with an overview/focused neighborhood. Show counters for busy ports instead of flashing for every sample. Preserve reduced-motion support. Port activity rate is the rate of **captured wrapper observations**, not automatically the actual hardware sampling rate; show loss and scope next to any rate.

Recommended labels:

```text
Connected debug producer | Model matched | Source stale
Evaluated: 42 consistent, 1 different, 3 not comparable
Applied transitions observed: 8
Capture: prefix evicted; 12 observations dropped; tail open
Last observed state: BUFFERING, 2.1 s ago
```

These counts are an illustrative layout, not results from this repository. Do not use a universal `LIVE PROVEN` or green badge suggesting that the entire app/spec has been proven.

### Comparison rules

- Evaluate each comparable observation using the exact loaded product kernel.
- Keep per-event `consistent`, `different`, `unavailable` results separate from capture completeness and source freshness.
- A structurally valid contradictory observed result is retained as disagreement; do not drop the interesting bad outcome solely because it differs from the model.
- A protocol-malformed event is rejected as invalid input, not transformed into a domain failure or a success.
- Unknown cell/state IDs in a declared target may be a useful runtime contradiction; preserve bounded raw diagnostics and locate the declared facet when the stronger cell key cannot be resolved. Never fabricate an entity.
- A disconnected, truncated or partially compared window may contain real contradictions and positive observations, but cannot receive an unqualified whole-capture success verdict.
- Existing loaded laws and WHAT/WHY validation cannot clear a live observation gap. An active socket by itself supplies zero behavioral evidence.

For machine continuity checks, require the same facet and explicit instance, applied observations, and an uninterrupted relevant sequence. Missing observations invalidate continuity claims, not necessarily each independently comparable finite evaluation.

### Read-only agent interface

Implement the `live` command as a small client of the same receiver snapshot/query functions used by the UI. Return a schema version, session/capture ID, model identity, cutoff/watermark, bounds and counters with every response. Pagination is pinned to an immutable cutoff; if it is evicted, return `live.cursor-expired` with a recovery action rather than mixing snapshots.

Use a same-user, access-restricted local discovery receipt to find the enabled instance. Do not place the UI's write-capable token in that receipt. Issue a separate read-only credential; verify its workspace and lifetime. Pure reads cannot pair a producer, export files, invoke `record` or access arbitrary model paths. `--freeze --output` is an explicit local export operation.

Return source/entity references, not executable remediation scripts. Treat all source comments, producer labels and summaries as untrusted data for an LLM. No embedded chat, paid API calls, MCP server or agent-specific prompt DSL is required. Existing exact-source navigation and bounded JSON are sufficient for the first implementation.

## 14. Errors must explain the next safe action

Stable error codes are part of the DX contract. Human output is short English; machine output includes the same code and bounded structured context, with no secrets.

| Code | Meaning / safe action |
|---|---|
| `live.disabled` | Receiver is off. Explicitly start Studio with live observation enabled. |
| `live.pairing-required` | No valid producer ticket. Pair from the local Studio UI. |
| `live.ticket-expired` | Ticket expired or was already used. Create a fresh one; do not retry it indefinitely. |
| `live.origin` | Browser Origin was not approved. Show the exact local origin that needs owner approval. |
| `live.model-mismatch` | Build identity differs. Show short expected/reported digest prefixes and product IDs; open the matching build. |
| `live.kernel-unavailable` | Exact evaluator missing. Inspect without comparison or use the owner's locked setup. Never silently upgrade. |
| `live.protocol-version` | Client and server protocol majors differ. Identify supported versions. |
| `live.sequence` | Duplicate/backward/unexplained sequence. End that capture and retain the diagnostic. |
| `live.overloaded` | Buffer/comparison budget exhausted. Narrow capture scope or lower observation volume. App remains unaffected. |
| `live.cursor-expired` | Requested retained window was evicted. Freeze a new window or open a saved trace. |
| `live.device-selection` | Multiple/no authorized ADB devices. Require an explicit serial; never pick the first. |
| `live.release-disabled` | App build lacks the debug adapter. Use the owner's debug build; no bypass flag. |

For browser connection failures, distinguish refused origin, incompatible protocol and general transport failure where observable. Do not pretend JavaScript can always identify the precise CSP/mixed-content/network cause; provide browser-console and same-origin troubleshooting steps when the platform only exposes a generic error.

## 15. Delivery slices and implementation order

Each slice is a reviewable PR with its own evidence boundary. No GitHub Actions, automatic merge gates, remote runners or release jobs. The owner or designated implementing agent runs checks on the owner's hardware when authorized. This planning PR runs none of them.

| Slice | Concrete deliverable | Exit criterion | Do not include |
|---|---|---|---|
| W0: baseline and integrity | Reconcile reviewed base with current main and #300; write exact source/kernel compatibility notes | Relevant existing integrity corrections reviewed and locally verified; no stale green claims | Redesign, dependency upgrades merely to satisfy Studio |
| W1: semantics and offline compatibility | Transport-free raw observation seam; shared normalization; trace v2 reader/writer and golden vectors | File/test paths remain compatible; evaluated/applied and loss cases cannot be confused | Sockets, Android networking, UI overhaul |
| W2: first local vertical slice | Loopback WS receiver, pairing and Node debug client; public reference app | Click ordinary demo action -> actual captured evaluation -> existing trace graph; disconnect leaves app working | App control, cloud, another graph |
| W3: inspect/freeze/agent DX | Existing-view live overlay, immutable capture windows, v2 export/import, bounded JSON client | Human and agent inspect the same cutoff; saved disagreement survives reopen | In-app AI chat, MCP, auto repair |
| W4: Android pilot | Debug-only transport, generated identity/bootstrap, selected ADB path, real owner observation where available | One emulator and one named USB device; evaluated versus applied state demonstrated; release isolation checked | Generic RPC, native debugger, new foreground service |
| W5: local-web pilot | Browser-safe observation entry and one opt-in Vite adapter | One real local web project; HMR/SSR isolation; production bundle contains no active bridge/credential | Universal browser/framework adapters |
| W6: public release and video | Packaging/license approval, public examples, current guides, support matrix, release notes and demo evidence | Release checklist below satisfied for the exact published artifacts | More feature families |

W4 and W5 consume the same protocol and do not fork it. If a platform cannot meet safety/identity requirements, explicitly label it unsupported/experimental; do not weaken the core to make the demo connect. A preview of a supported subset may ship with a truthful matrix rather than blocking the already-useful offline core indefinitely.

### Product-specific handoff

- **CircleKit:** own shared protocol, hooks, emitters, receiver, graph and public demo. Keep source-first authoring and product-owned compilers.
- **SKYVW native:** begin with the existing recording-machine/power-rule hook locations. Inspect the actual state owner before promising applied transition capture. Preserve sensor inputs, thresholds, release behavior and `LIVE_SHARE.reason`. Existing public PR claims about test output are not new verification.
- **SKYVW web:** begin with the existing named binding boundary. A function returning a model/callback is not proof of account transport success. Browser and SSR are different producers.
- **AMUX policy:** observe its existing decision table without launching provider/bridge sessions. Link's kernel and generated-ID mapping remain its own. Do not invent machine traces where no machine runs.
- **ai-dsl:** keep activity as a projection of backend-owned job state, not a new scheduler. Instrument the actual runtime decision path, not build-time enumeration of all table points. No GPU/provider job is started to make a demo interesting.

## 17. Open-source release, adoption and video

### Release is more than completing the socket

At the reviewed commit, Studio requires local linking and reports `private: true`/`UNLICENSED`; ProductSpec also reports `UNLICENSED`. Do not call those artifacts ready for public open-source reuse. Before publication, the owner must approve the license and licensing scope across the actually distributed code and dependencies. This PR deliberately changes no legal rights or package publication settings.

Release checklist:

- [ ] Owner-approved license, correct package metadata/notices and compatible redistribution for every shipped component.
- [ ] Exact public CLI/client artifacts and dependency pins are accessible; no private test fixtures, sibling-checkout requirements or private source/media in the package.
- [ ] One documented installation route from the released artifact, plus source-checkout instructions. Do not advertise an unverified `npx` package name/version.
- [ ] Public reference app includes its own declarations, generated model, source and fake data. It does not require SKYVW credentials or private app code.
- [ ] Mandatory AMUX wording validation can resolve a supported public dependency/path. Do not quietly drop grammar checks or copy a second linter to make setup work.
- [ ] Compatibility matrix names tested Studio protocol/trace versions, ProductSpec versions, Node/browser versions and Android build/device conditions.
- [ ] Runtime bridge is explicitly opt-in, development-only and observation-only. Security reporting channel and limitations are documented.
- [ ] One quickstart, one integration guide and this protocol/decision reference are sufficient; remove obsolete setup claims when implementation lands, not useful historical evidence in other agents' PRs.
- [ ] Integrity and release-isolation checks are locally evidenced against exact release bytes. No CI is created for this work.
- [ ] A new developer can complete the documented first capture without the maintainer repairing their environment. Record actual attempts and failure points.

### Adoption measurements instead of feature count

Use a small pilot of independent developers/agents completing the same concrete questions with and without Studio: identify owner, locate consumers, explain the boundary, find the disagreement, open the right source. Record successful task completion, files/searches needed, setup interventions and time. These are descriptive pilot results, not a claim of statistically proven industry-wide productivity.

Proposed usability target: a configured sample produces the first meaningful observation within two minutes of following its quickstart, without editing a hash or writing an event. This is an acceptance target, not a completion-time promise. Existing-app setup and first-time SDK installation are reported separately.

### A video that demonstrates the value

Suggested 120-second structure, recorded only after the implementation works:

| Segment | Show | Claim allowed |
|---|---|---|
| 0-20 s | One declared machine/boundary; open Studio | Structure comes from the supplied product declaration, not a separately maintained diagram. |
| 20-40 s | Click owner, WHAT/WHY, inputs, consumer and source | Exact declarations and source links explain this selected scope. |
| 40-65 s | Interact with the running public demo; observe evaluation and applied-state labels | These instrumented calls/results were captured from this debug app. |
| 65-85 s | Real demo owner commits a deliberately wrong result | Studio identifies the disagreement against the matching model. |
| 85-105 s | Freeze, reopen capture, agent reads same cutoff | The same bounded evidence is inspectable without the original live connection. |
| 105-120 s | Optional split screen with desk-connected phone, then install/quickstart link | Show Android only if its adapter and device path were verified. |

Use synthetic/demo data visibly. Do not show real location/audio/account information. Do not label a modified trace file as a real live fault. Avoid `proves your app`, `replaces all debugging`, `no instrumentation` or `Mermaid is obsolete`.

Suggested positioning:

> Product Studio connects declared architecture to observed behavior. Inspect the same model in source, a running debug app and a saved capture.

## 18. Explicitly deferred

Control/injection is a separate future proposal with per-action allowlists, product-side authorization, explicit operator consent, idempotency/cancellation, timeout semantics and injected-stimulus provenance. It must not reuse an observation credential. No generic control handler or `invoke` route should be prebuilt under this plan.

Arbitrary object/memory inspection, requested app snapshots, breakpoints, app pause, hot reload orchestration, time-travel execution, live production support, remote tunnels, OTLP/DAP/MCP, framework-wide auto-discovery and general-purpose effect mocks are deferred. A saved trace replays observations; it does not replay the application.

If the three-event-family loop is not useful on the real pilots, improve or narrow that loop before adding these features. Once the stated release slice works, stop expanding it and ship the documented scope.

## 19. Handoff and completion definition

Read sections 1, 2, 7, 8, 9 and 15 before implementation. Preserve the current product kernels, existing pure imports, viewer-only default and separation of declared/test/runtime evidence.

The implementer should report, per slice: exact commits changed; source-grounded decisions; owner-local checks actually run; observed failures and fixes; shipped platform scope; remaining unknowns. A screenshot, completed shell command or positive PR description is not independent proof of the underlying behavior.

**Planning deliverable complete:** this document and its review PR exist and are reachable.

**Implementation complete:** the scoped adapters, receiver, shared trace path and UX exist, required acceptance cases have real owner-local evidence, release artifacts satisfy the support matrix and no blocking security/integrity defect is hidden behind a green label.

**Still requires owner decisions:** licensing/publishing rights and actual release authorization. **Still requires implementation evidence:** platform compatibility, disabled/release isolation, measured overhead and usability. These are not silently resolved by this plan.
